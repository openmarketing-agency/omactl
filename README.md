# omactl

One local CLI for installing, operating, verifying, backing up and updating an Open Marketing Agency instance. Runtime requirements: Docker Engine 24.0+ with Compose 2.24+ (Docker Desktop, OrbStack and Colima are supported through the active Docker context).

Pushing a version tag builds the Linux x86-64 package `omactl-linux-x64.tar.gz` with `bin/omactl`, `catalog/`, and the license. Verify it against `SHA256SUMS` on the same [GitHub release](https://github.com/openmarketing-agency/omactl/releases) before extracting.

Start with the [user guide](docs/USER_GUIDE.md) for installation, the local demo, day-to-day commands, backups, recovery, updates, and troubleshooting.

```sh
bun install --frozen-lockfile
bun run typecheck
bun test test/unit
bun run build
```

Bun **1.4.4** is pinned in `package.json` and CI. `dist/` receives standalone Linux x64/arm64, macOS x64/arm64, and Linux musl x64/arm64 executables. `bun run build --current` builds only the local target.

Try the fixture apps on an isolated Docker instance:

```sh
docker build --build-arg APP_VERSION=1.0.0 -t omactl-testapp:1.0.0 fixtures/testapp
./dist/omactl-darwin-arm64 init --catalog catalog --http-port 18080
./dist/omactl-darwin-arm64 install --bundle notes-demo
./dist/omactl-darwin-arm64 verify --all --json
./dist/omactl-darwin-arm64 backup init --repository "$PWD/backups"
./dist/omactl-darwin-arm64 backup run --all
```

Choose the binary matching your platform. Source development uses `bun run dev -- <command>`. `OMA_HOME` defaults to `~/.oma`; use `--home` for another directory. Only one instance runs on a Docker daemon because app projects, volumes, and the edge network have fixed names.

Every command supports `--json`. Run changes with `--plan --json` to inspect steps first. Purge, restore, pruning, and binary rollback require a matching `--confirm` target. Configure a backup repository before updates or removal. Reinstalling an app with retained volumes recovers its original credentials from the final backup. Backups can use a local directory or S3-compatible storage; pass credentials through `backup init --env-file`.

```sh
omactl install testapp --plan --json
omactl status --json
omactl restore testapp --latest --confirm testapp --json
omactl history --limit 10 --json
```

The catalog contains Traefik, [WordPress](catalog/apps/wordpress/README.md), [Ghost](catalog/apps/ghost/README.md), [Umami](catalog/apps/umami/README.md), [Listmonk](catalog/apps/listmonk/README.md), and the purpose-built `testapp` / `testclient` fixtures. Add new apps as catalog folders following [CATALOG.md](docs/CATALOG.md). The maintenance agent contract is [AGENT.md](docs/AGENT.md); implementation and release details are in [ARCHITECTURE.md](docs/ARCHITECTURE.md). JSON Schemas are generated by `bun run schemas`.

Run the complete Docker acceptance suite on an isolated daemon, after building both fixture tags:

```sh
docker build --build-arg APP_VERSION=2.0.0 -t omactl-testapp:2.0.0 fixtures/testapp
OMA_E2E=1 bun run test:e2e
```

The fixture suite refuses existing OMA containers, uses port 18080 and `.e2e/`, starts a local signed release server, and cleans up its own containers/volumes. It includes all 16 scenarios from the build spec. Without `OMA_E2E=1`, Docker tests are skipped.

The tag workflow publishes the portable Linux package with the repository catalog. The demo catalog entries use local fixture images. To publish the signed update channel, run the release workflow manually with `OMA_RELEASE_PUBLIC_KEYS` configured as an Actions variable and `OMA_RELEASE_PRIVATE_KEY` configured as an Actions secret. For `bun run release` locally, also set `OMA_RELEASE_ASSET_URL`.

The WordPress integration test checks setup, REST verification, and recovery of a post and upload after loss of the database volume:

```sh
OMA_WORDPRESS_E2E=1 bun test --timeout 600000 test/e2e/wordpress.test.ts
```

Run it on an isolated Docker daemon after the fixture suite has cleaned up. CI runs both suites on Linux x64 and arm64.

The Ghost integration test checks repeated setup, database writes, image serving, and recovery of settings and content after database-volume loss. It uses unique temporary projects and volumes:

```sh
OMA_GHOST_E2E=1 bun test --timeout 600000 test/e2e/ghost.test.ts
```

The Umami integration test checks default-password replacement, repeated setup, pageview collection and reporting, and recovery of analytics after database-volume loss. It also uses unique temporary projects and volumes:

```sh
OMA_UMAMI_E2E=1 bun test --timeout 600000 test/e2e/umami.test.ts
```

The Listmonk integration test checks repeated setup, authenticated list/subscriber operations, upload persistence, and logical restore after database-volume loss. It uses unique temporary projects and volumes and can coexist with installed apps:

```sh
OMA_LISTMONK_E2E=1 bun test --timeout 600000 test/e2e/listmonk.test.ts
```
